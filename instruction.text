# Project Specification: Personal AI Job Search and Auto-Apply Agent

## 1. Project Objective

Build a full-stack, locally running AI-powered job search and application platform using React.js, Node.js, Express.js, MongoDB, Docker, and the OpenRouter API.

The application must run on my laptop. The Express backend and MongoDB must run in Docker containers. The React frontend should run locally during development and communicate with the backend through a REST API.

The AI agent should:

1. Read and analyze three CVs and three corresponding cover letters from a configurable local folder.
2. Create separate candidate profiles for three career paths.
3. Discover relevant job vacancies in Germany and remote EU locations.
4. Evaluate job descriptions against my CVs and rank vacancies by relevance.
5. Select the appropriate CV and cover letter for each vacancy.
6. Generate a tailored cover letter when needed, using only verified information from my profile.
7. Automatically prepare and submit applications through supported and permitted application channels.
8. Store jobs, matching results, documents metadata, and application history in MongoDB.
9. Provide a React dashboard for monitoring jobs, applications, errors, and agent activity.

Do not build only a UI prototype. Implement a functional, modular application with working backend APIs, persistent storage, tests, Docker configuration, and setup documentation.

## 6. Job Discovery Integrations

Implement a modular job-source adapter architecture.

Potential sources:
- Official job-search APIs.
- Approved job-board APIs.
- Public company career pages where access is permitted.
- Employer-provided application APIs.
- Other sources with documented, permitted access.

Each adapter should expose a common interface:

```ts
interface JobSourceAdapter {
  searchJobs(criteria: JobSearchCriteria): Promise<JobListing[]>;
  getJobDetails(jobId: string): Promise<JobListing | null>;
}
```

The precise interface may be adjusted to fit the implementation.

Requirements:
- Never invent job listings.
- Preserve the original job URL, employer, title, location, description, source, publication date if available, and application URL.
- Normalize job listings into a common schema.
- Detect duplicate vacancies using source IDs, canonical URLs, and normalized employer/title combinations.
- Record when each job was discovered and last verified.
- Mark expired or unavailable listings.
- Handle missing descriptions and failed source requests gracefully.
- Respect source terms, rate limits, authentication requirements, and robots or access restrictions where applicable.
- Do not bypass CAPTCHAs, anti-bot measures, authentication controls, or other access restrictions.
- Do not depend on one job board.

If a source requires credentials or API access, provide a configuration guide and a clear disabled status until configured. Never claim an integration works unless it has actually been implemented and tested.

## 9. Job Matching Engine

Use a hybrid matching strategy.

First, apply deterministic filters:
- Target role.
- Country and location.
- Work arrangement.
- Language requirements.
- Minimum salary if configured.
- Job freshness.
- Duplicate and previous-application checks.

Then use AI to evaluate:
- Technical skill overlap.
- Relevant professional experience.
- Seniority.
- Responsibilities.
- Required and preferred qualifications.
- Domain relevance.
- Language and location fit.
- Missing or uncertain requirements.

Return validated structured results:

```ts
interface JobMatchResult {
  jobId: string;
  profileId: string;
  score: number;
  matchedSkills: string[];
  missingSkills: string[];
  strengths: string[];
  concerns: string[];
  explanation: string;
  recommendedCvDocumentId: string;
  recommendedCoverLetterDocumentId: string;
}
```

The score must be between 0 and 100.

Show the reasons for each score rather than presenting it as a probability of getting hired.

Use deterministic scoring for important mandatory requirements and AI-assisted scoring for semantic relevance. Store the score, evaluation date, model ID, and prompt version.

Do not apply automatically when mandatory requirements are unknown or when the job is a poor match.

## 11. Application Automation

Implement a workflow that supports both preparation and controlled submission.

Application states:

```text
DISCOVERED
MATCHED
READY_FOR_REVIEW
APPROVED
SUBMITTING
SUBMITTED
FAILED
NEEDS_MANUAL_ACTION
WITHDRAWN
```

The default mode must be `approval_required`.

Before submission:
1. Verify that the vacancy is still available.
2. Confirm the job has not already been applied to.
3. Confirm that the CV and cover letter belong to the correct career profile.
4. Generate or retrieve the final cover letter.
5. Identify mandatory application questions.
6. Confirm all required answers are known and accurate.
7. Display the complete application summary for review.
8. Require explicit user approval.

Use official APIs or permitted browser automation where available.

For browser automation, use a separate Playwright service or module and implement site-specific adapters. Never assume every website shares the same form layout.

Do not:
- Bypass CAPTCHA or anti-bot systems.
- Evade access controls.
- Fabricate answers to screening questions.
- Guess legal declarations.
- Claim a submission succeeded without confirmation.
- Submit applications to unrelated roles merely to increase volume.
- Repeatedly retry non-idempotent submission actions without verifying the outcome.

If an employer requires a manual action, account login, CAPTCHA, or unanswered legal declaration, set the state to `NEEDS_MANUAL_ACTION` and explain what I need to do.

Implement an application-level approval record with a timestamp, job ID, document versions, and the user's confirmed answers. Enforce approval on the backend, not just in the frontend.

The backend must reject any submission without a valid approval record for that specific job and application version.

If I later enable unattended submissions, provide an explicit setting with strict eligibility rules and a clearly defined limit. Keep legal declarations and other personal attestations subject to my confirmation.

## 12. MongoDB Data Models

Use MongoDB with Mongoose.

Create collections/models for:

### CandidateProfile
Stores candidate preferences, skills, and profile-to-document mappings.

### Document
Stores file metadata, content hash, extracted text, type, and processing status.

### Job
Stores normalized job listings, source information, employer, URL, location, description, and freshness.

### JobMatch
Stores profile-specific scores, matched skills, missing skills, explanation, model, and evaluation timestamp.

### Application
Stores job ID, profile ID, selected documents, cover letter version, status, approval record, submission result, and timestamps.

### SearchRun
Stores job discovery run status, counts, duration, source errors, and timestamps.

### AppSetting
Stores non-secret settings such as search filters, schedule, scoring thresholds, and selected model ID.

Never store API keys in ordinary MongoDB documents or expose secrets through the API.

Add indexes for:
- Unique source/job identifiers where available.
- Normalized job URL.
- Application duplicate detection.
- Job status and discovery date.
- Match score and candidate profile.
- Application status and creation date.

Use migrations or documented initialization scripts where schema changes require them.
